# PR: Fix deploy.sh Go install + service startup, and investigation empty-result handling

## Summary

This PR fixes three defects that prevented a clean `sudo ./deploy.sh` on Amazon
Linux 2023 and one runtime bug that made valid investigation scenarios fail with
a generic "An internal error occurred" message.

All issues were found and verified end-to-end on a live AL2023 EC2 host
(`x86_64`, DuckDB CLI v1.2.2, Go 1.26.4).

Base branch: `main` (at `e0d4511`)

---

## Changes

### 1. `deploy.sh` — Go tarball checksum verification (deploy blocker)

**Problem:** `install_go()` fetched a checksum sidecar at
`https://go.dev/dl/go<ver>.linux-<arch>.tar.gz.sha256`. That URL does **not**
exist on go.dev — it returns an HTML redirect page with HTTP 200, so the
`|| fail` guard never fired. The code then parsed `<!DOCTYPE` as the "expected"
checksum, `verify_sha256` saw a mismatch against the real tarball, and the
script aborted. With Go never installed, the build never ran and the service
never started.

**Fix:** Pin the official Go SHA-256 checksums per architecture (sourced from
`https://go.dev/dl/?mode=json`) and verify against them via the existing
`verify_sha256` helper — mirroring how Node.js (`NODE_SHA256`) and DuckDB
(`DUCKDB_SHA256`) are already handled in the same script. Fail-closed and no
fragile runtime lookup.

### 2. `deploy.sh` — state directory ownership (service startup crash loop)

**Problem:** The script created `DATA_DIR=/var/lib/cloudtrail-analyzer/data`,
which left the parent `/var/lib/cloudtrail-analyzer` owned by `root:root` mode
`700`. Step 10's `chown -R` targeted only `$DATA_DIR`, never the parent, so the
`cloudtrail` service user could not traverse into it. The service crash-looped
with:

```
creating data directory /var/lib/cloudtrail-analyzer/data: mkdir ... permission denied
```

**Fix:** Introduce `STATE_DIR=/var/lib/cloudtrail-analyzer`; create/`chmod` it,
`chown -R` it (covering `data`), and set the systemd unit's
`ReadWritePaths=${STATE_DIR} ${APP_DIR}` so the sandbox permits writing the
whole state tree.

### 3. `deploy.sh` — misplaced systemd keys (spurious warnings)

**Problem:** `StartLimitIntervalSec` / `StartLimitBurst` were under `[Service]`,
where systemd ignores them and logs `Unknown key name ... ignoring`.

**Fix:** Move both keys to `[Unit]`, where they belong.

### 4. `internal/features/nlquery/investigate.go` — empty-result handling (runtime bug)

**Problem:** Investigation scenarios wrap their query with
`COUNT(*) OVER () AS __investigation_total_rows` to report the total row count.
When a scenario matches **zero rows**, DuckDB's CSV output for a windowed query
is completely empty (no header row), so `executeDuckDB` returns empty
columns/rows with no error. `extractInvestigationMetadata` then treated empty
columns as a hard failure (`"investigation result is missing total-row
metadata"`), which the UI surfaced as the redacted "An internal error
occurred / Query Error".

This affected **any** scenario matching zero rows (e.g. "IAM Write Operations"
and "IAM Activity by Access Key" when the synced window contains no IAM events).

**Fix (two parts):**
- `extractInvestigationMetadata`: treat empty columns + empty rows as a
  legitimate empty result set (return `0` total rows, no error). The
  malformed-result guard is preserved for the case where columns are present
  but wrong.
- `RunScenario`: on a successful zero-row result, add an explicit
  `message` field:
  `"No matching events found for this investigation in the selected time window and account scope."`
  so the response is self-describing for API consumers and the UI, and is
  clearly distinguished from an error.

### 5. `web/src/features/query/InvestigateView.tsx` — surface the message

Added `message?: string` to the result type and made the existing empty-state
render `result.message` when present, falling back to the existing i18n
"No results found" text.

### 6. `internal/features/nlquery/service_test.go` — fix pre-existing broken test

`TestExecuteDuckDB_EmptyResult` was **already failing on the clean baseline**
(confirmed via `git stash`), independent of the changes above. It expected 1
column header for a zero-row query, but DuckDB v1.2.2 emits no header at all for
an empty CSV result — the same behavior at the root of defect #4. Updated the
assertion to expect `0` columns and documented why.

## Notes for the reviewer

- Defect #4 is the user-facing bug; the empty result is expected when the synced
  time window/account scope contains no matching events. The UI now states this
  clearly instead of showing an error.
- When bumping `GO_VERSION` in `deploy.sh`, update both `GO_SHA256` values (a
  maintainer comment with the exact fetch command is included in the script).
